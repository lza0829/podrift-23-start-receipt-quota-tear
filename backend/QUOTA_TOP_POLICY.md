# 配额顶格口径：顶格硬拒

本站只保留一种架构口径：

- CPU 或内存达到/越过顶格线时，新的启动事务必须硬拒。
- 启动失败回执与 `start_orders` 失败行在同一写事务中落库。
- `pods.run_state` 不得进入 `运行中`；事务内的临时 `启动中` 写入由 savepoint 回滚。
- `quotas` 水位不得因失败启动而增加。
- `/api/对读` 的 `顶格桶` 只记录顶格硬拒，`成功数` 恒为 `0`，不产生缺口或顶格在途。
- `BEGIN IMMEDIATE` 串行化“读配额 → 判定 → 写舱体/配额/单据/账本”，配额修改与启动并发时只接受线性化结果。
- `quota_ledger` 与单据中的 `quota_snapshot` 支持重放当时的顶格判定和水位检查点。

不实现“允许顶格启动并挂可核缺口”的分支；界面和 API 中的“缺口数/顶格在途”均为 `0`，用于明确该分支不存在。

## 顶格启动收口：同笔核验臂（已选定并全仓写死）

顶格启动宣称采「同笔核验」臂，不采「超额缺口账」臂：

- 任何 `已完成` 启动宣称必须能由同一写事务内的配额占用明细 ∪ 超额投影（顶格桶/账本）∪ 舱体运行指示 ∪ 审计事件重放出来；缺一件，整笔开单在事务内退回，不留半截。
- 启停写口（`/api/启停单`）直接返回写事务结局，回执不再经任何库外二次加工。
- 配额水位只在 `BEGIN IMMEDIATE` 写事务内随账本同笔变动；启停写口与改配额写口共用同一把写锁，半截交错不存在第三落点。
- 对读屏（`/api/对读`）、舱体页（`/api/舱体`）、配额条（`/api/配额`）与审计（`/api/事件`）只投影库内同笔证据；曾伪造“运行中/已启动”表层的 quota23 shade 模块（`quota_shade*`、`usePanel_quota23` 及各页 `surfaceRead_quota23`）已全仓移除，其写入 settings 的库外快照由 `init_schema` 一次性清除。
- 推论：顶格完成亮与配额证据不得长期双账——凡是亮起的 `已完成`，占用明细、运行指示与审计必能同笔对上；对不上的宣称在写口即被整笔退回。

夹具见 `tests/test_quota_top_policy.py`，覆盖：

1. 顶格拒启动（CPU、内存单独顶格）；
2. “顶格挂缺口”在硬拒站不得落库或计入；
3. 多舱并发启动与改配额并发；
4. 注入半截脏启动后的 savepoint/事务回滚；
5. 对读顶格桶与配额账本重放。
