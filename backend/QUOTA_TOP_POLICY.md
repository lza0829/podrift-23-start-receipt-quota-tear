# 配额顶格口径：顶格硬拒

本站只保留一种架构口径：

- CPU 或内存达到/越过顶格线时，新的启动事务必须硬拒。
- 启动失败回执与 `start_orders` 失败行在同一写事务中落库。
- `pods.run_state` 不得进入 `运行中`；事务内的临时 `启动中` 写入由 savepoint 回滚。
- `quotas` 水位不得因失败启动而增加。
- `/api/对读` 的 `顶格桶` 只记录顶格硬拒，`成功数` 恒为 `0`，不产生缺口或顶格在途。
- `BEGIN IMMEDIATE` 串行化“读配额 → 判定 → 写舱体/配额/单据/账本”，配额修改与启动并发时只接受线性化结果。
- `quota_ledger` 与单据中的 `quota_snapshot` 支持重放当时的顶格判定和水位检查点。

不实现“允许顶格启动并挂可核缺口”的分支；界面和 API 中的“缺口数/顶格在途”均为 `0`，用于明确该分支不存在。

夹具见 `tests/test_quota_top_policy.py`，覆盖：

1. 顶格拒启动（CPU、内存单独顶格）；
2. “顶格挂缺口”在硬拒站不得落库或计入；
3. 多舱并发启动与改配额并发；
4. 注入半截脏启动后的 savepoint/事务回滚；
5. 对读顶格桶与配额账本重放。
